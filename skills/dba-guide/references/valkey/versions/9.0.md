# Valkey 9.0

Checked: 2026-11-27. Read this when the server reports `valkey_version:9.0.x`, when moving from 8.x to 9.x, or when deciding whether a 9.x node can be rolled back.

## Lifecycle

- First release 2025-10-21. Maintenance and security support both end 2028-10-21; no extended window (https://valkey.io/topics/releases/).
- Latest patch on 2026-11-27: 9.0.8 (2026-11-18, security).
- RDB version 80, file magic `VALKEY` instead of `REDIS`. Versions 12 to 79 are reserved as "foreign" (non-OSS Redis) formats and refused.

## Changed Defaults

- `TCP_NODELAY` is enabled by default on incoming and outgoing connections (9.0.0-rc1, #1763).
- `CONFIG GET` returns sorted output (9.0.0-rc2).
- `io-threads` can be changed at runtime with `CONFIG SET` (9.0.0-rc1, #2033); earlier series need a restart.
- New settings: `cluster-databases` (default 1), `cluster-announce-client-port`, `cluster-announce-client-tls-port`, `tls-auth-clients-user` (default `off`), `mptcp` and `repl-mptcp` (default `no`), `slot-migration-max-failover-repl-bytes`, `cluster-slot-migration-log-max-len` (defaults from the 9.2 image).
- A cluster primary can trigger a manual failover to a replica before shutting down (#1091, unified config #2292). In the 9.0.8 image this is the `failover` value of `shutdown-on-sigterm` and `shutdown-on-sigint` (both default `default`) and the `SHUTDOWN FAILOVER` modifier; 8.1 rejects `failover`.

## Removed or Deprecated

- "Most deprecated commands are now un-deprecated" (9.0.0-rc2, #2546). Commands that 7.x docs called deprecated remain available.
- Behavior changes (9.0.0 notes, AWS list): authentication is checked before command existence and arity, so unauthenticated clients get an authentication error instead of "unknown command"; errors inside `MULTI/EXEC` name the full command (`CLIENT SETNAME`); `GEOSEARCH` shape errors mention `BYPOLYGON`; `SCRIPT EXISTS`, `SCRIPT SHOW`, `SCRIPT FLUSH` get the `STALE` flag.
- 9.0.5: strict CRLF parsing. 9.0.6: `HGETEX` requires write permission; `HPERSIST`, `HTTL`, `HPTTL`, `HEXPIRETIME`, `HPEXPIRETIME` return a syntax error without the `FIELDS` keyword; `sanitize-dump-payload` becomes a no-op.

## Worth Adopting

- Hash field expiration: `HEXPIRE`, `HPEXPIRE`, `HEXPIREAT`, `HPEXPIREAT`, `HTTL`, `HPTTL`, `HEXPIRETIME`, `HPEXPIRETIME`, `HPERSIST`, `HSETEX`, `HGETEX`. Expired fields are removed by a periodic job; commands treat them as missing at once. In 9.0 and 9.1 a hash with any field TTL is stored as `hashtable` (official 9.0 image: `OBJECT ENCODING` `hashtable`, `MEMORY USAGE` 256 bytes for a 3-field hash), so field TTLs cost memory on small hashes; 9.2 keeps small ones as `listpack`. Use 9.0.2 or later: 9.0.2 fixed several hash-field-expiration bugs.
- `DELIFEQ key value`: delete only if the value matches (safe lock release without Lua).
- Numbered databases in cluster mode (`cluster-databases N`, `SELECT` works in a cluster). See [replication-and-cluster.md](../replication-and-cluster.md) for caveats.
- Atomic slot migration: `CLUSTER MIGRATESLOTS SLOTSRANGE a b NODE <id>`, `CLUSTER GETSLOTMIGRATIONS`, `CLUSTER CANCELSLOTMIGRATIONS`. Faster and fewer client errors than `CLUSTER SETSLOT` + `MIGRATE`.
- `CLUSTER FLUSHSLOT`, `CLUSTER REPLICATE NO ONE`, `SHUTDOWN SAFE` (refuses shutdown in unsafe situations).
- Automatic client authentication from TLS certificate CN (`tls-auth-clients-user CN`).
- Pipelining throughput: multiple commands parsed and prefetched at once (#2092).
- `GEOSEARCH ... BYPOLYGON`, MPTCP, lttng tracing, `valkey-cli --hotkeys-count`.

## Upgrading Into This Series

From 8.1 (or 8.0):

1. Rollback planning first: once a 9.0 primary writes an RDB or AOF base, 8.0 and 7.2 cannot load it. 8.1 can load it with `rdb-version-check relaxed` only while no new types were written: 8.1.12 loaded a strings-only 9.0.8 RDB and exited on one with a field-TTL hash (`Unknown RDB encoding type 22`). Keep an 8.x replica detached (`REPLICAOF NO ONE`) or a pre-upgrade RDB until the 9.0 rollout is accepted. Replication from a 9.0 primary to an older replica uses a backward-compatible format, but writes using new types cannot be represented.
2. Modules: atomic slot migration is disabled in clusters that load a module that has not opted in. Check module versions before relying on `CLUSTER MIGRATESLOTS`.
3. ACLs: with atomic slot migration, the target applies migrated data as the `primaryuser`; that user needs `+@write ~* -@dangerous +ping +select +psync +replconf +cluster|syncslots -flushall -flushdb -restore -restore-asking` (https://valkey.io/topics/atomic-slot-migration/).
4. Client libraries: check how they handle authentication errors that now arrive before command validation and, if you plan to use `cluster-databases > 1`, whether they allow `SELECT` in cluster mode.
5. When continuing to 9.1 later, use 9.1.3 or later (listpack incompatibility fix for mixed 9.0/9.1 nodes).

## Managed Service Notes

- ElastiCache "9.0 for Valkey" adds ElastiCache-only features: durability through a Multi-AZ transactional log (synchronous or asynchronous writes), public endpoints for Serverless (IAM auth and TLS 1.3 required), and full-text/hybrid search from valkey-search. These are not part of upstream 9.0.
- ElastiCache parameter family `valkey9` (`default.valkey9`, `default.valkey9.cluster.on`) covers 9.0 and 9.1 and is incompatible with 8.x and Redis OSS groups. ElastiCache documents `cluster-databases` with range 1 to 10,000, default 0, set at creation and not modifiable afterwards (the documented default 0 conflicts with the upstream default 1 and with the range).
- MemoryDB lists no 9.x Valkey engine on 2026-11-27.
