### 경미 (1)

#### [경미] 하나의 할인 정책이 두 모듈에 중복 구현됨

- **파일**: `checkout.py:1`, `renewal.py:1`
- **문제**: README에서 하나의 정책으로 정의한 `discount_percent` 로직이 두 파일에 같은 코드로 각각 구현되어 있습니다.
- **근거**: 두 함수 모두 활성 회원이면서 `subtotal_cents >= 10000`일 때 `10`, 그 외에는 `0`을 반환합니다. 저장소 내 런타임 참조는 아직 없지만, 향후 임계값이나 할인율을 바꿀 때 두 구현을 각각 수정해야 합니다.
- **영향**: 한쪽만 수정되면 결제와 갱신 경로의 할인 결과가 달라질 수 있으며, 동일 정책의 검증과 변경 비용이 중복됩니다.
- **신뢰도**: 높음 (High)
- **제안**: 할인 정책을 공통 모듈의 단일 함수로 옮기고 `checkout.py`와 `renewal.py`가 이를 가져오게 하세요. 기존 모듈 경로가 공개 API라면 각 모듈에서 같은 이름으로 다시 노출해 호환성을 유지할 수 있습니다.

## 분석 한계

- 저장소 안에는 자동화 테스트가 없어 변경된 동작에 대한 회귀 테스트 보유 여부를 확인할 수 없었습니다. 대신 Python 컴파일, 공개 응답 계약, 소비자 호출, 할인 정책의 `9999`/`10000` 경계값을 직접 단언해 확인했습니다.
- 정적 검색은 현재 저장소 밖의 소비자를 확인할 수 없습니다. 다만 README는 `account_response()`를 공개 계약으로 명시하고 내부 레코드의 `status` 사용을 허용하며, 저장소 내 유일한 소비자도 유지된 `accountStatus`를 사용합니다.

## 좋은 점

- `account_record()`의 내부 키를 `status`로 바꾸면서 `account_response()`에서 `accountStatus`로 변환해 기존 공개 소비자 계약을 보존했습니다.
- 활성 회원 여부와 `10000`센트 임계값을 포함한 할인 동작은 README의 정책과 일치하며, 직접 실행한 경계값 검증도 통과했습니다.

## 결정 근거

- 공개 계약 파손이나 잘못된 경계값 동작은 확인되지 않았고, 발견 사항은 중복 구현에 따른 유지보수성 위험 1건입니다. 코드 리뷰 기준상 경미한 발견 사항만 있으므로 승인합니다.
