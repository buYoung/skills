## Update Scope

Update mode refreshes **only** standard sections in a document enrolled in this skill's management workflow. After the management gate below passes, every matched standard section is a managed replacement target: replace its body with freshly generated content even when the existing wording appears acceptable. Optional standard sections are kept only when fresh analysis finds evidence-backed content; otherwise omit the managed section instead of reusing old wording. All other content is user-owned and preserved exactly, except an approved management-marker insertion or document-type replacement in the preamble.

User-owned additions must live in non-standard sections, preferably `## Custom Instructions`. Do not add user-owned material inside standard managed sections, because those sections are fully refreshed from repository re-analysis during update mode.

```yaml
- target: Standard sections (managed by skill)
  action: Replace body with fresh managed content; omit optional sections with no current evidence
  reuse_old_body: false
- target: Custom sections (user-defined)
  action: Preserve unchanged, maintain original position
```

## Skill-Generated Files Only

The management marker records that the document was generated by this skill or explicitly adopted into its update workflow. It is an enrollment convention, not proof of original authorship. Heading matches only identify candidate replacement sections; they never establish enrollment.

### Management Marker and Early Gate

Use exactly one standalone `<!-- agents-md-generator: v1; doc-type: single_repo -->` line in the preamble before the first `##` heading. Use `monorepo_root` instead of `single_repo` for a monorepo root; packages use `single_repo`. New documents receive the marker during generation. Existing unmarked documents receive it only with approved adoption. Count its characters as preamble content.

Before LOC measurement or deep repository analysis, run the section parser on each existing target. Its existing fields and `--doc-type` argument retain their meanings, with two additive JSON fields:

- `management_status`: `managed` for exactly one supported standalone marker in the preamble; `unmarked` when no marker candidate exists; `invalid` for malformed, duplicate, unsupported-version, unknown-type, or misplaced marker candidates. Markers in fenced code blocks are ignored.
- `generated_doc_type`: the valid marker's `single_repo` or `monorepo_root`, otherwise null. `doc_type` still records the caller's requested matching set; the parser does not silently switch sets.

For `managed`, compare `generated_doc_type` with the current repository type before interpreting replacement ranges. A mismatch requires reparsing with the original type, then following the confirmed full-regeneration procedure below. For `invalid`, stop automatic updating and report the marker problem; do not silently repair or replace it.

### One-Time Adoption of Unmarked Documents

For `unmarked`, determine the original document type from distinctive standard headings: `## 3. Working Agreements` identifies a monorepo root, while `## 3. Core Behaviors & Patterns` or `## 5. Working Agreements` identifies a single repo/package document. If evidence is conflicting or insufficient, ask which original type to use before planning replacements. Parse with that original type to distinguish original standard and custom sections.

With one or more matched standard headings, prepare the complete proposed replacements, insertions, deletions, and marker insertion. Show this concrete preview and explain that matched sections become managed and will be replaced in future updates. Obtain one-time confirmation of that adoption before writing. A general request to update `AGENTS.md` is not adoption confirmation; confirmation already given for the concrete preview need not be requested again. Approval writes the refreshed document and marker together; refusal leaves the original unchanged. Type-transition approval can be combined with adoption approval in the same concrete preview.

With zero matching standard headings, do not insert a second set of sections or mark the file as managed. Report that selective updating is unavailable; full regeneration requires an explicit request. This also applies to a marked file whose standard headings have all disappeared. A lack of matching headings does not prove who authored the file.

The following YAML records the **superseded heading-only guard**, retained as historical context. Do not use its `Proceed with update mode` branch or authorship inference as the current management gate:

```yaml
- case: At least one standard heading matches
  action: Proceed with update mode
- case: Zero standard headings match (every section is custom)
  meaning: The file was authored outside this skill
  action: Do NOT modify the file; report the situation to the user and stop
  follow_up: Full regeneration only on the user's explicit request
```

The current gate prevents both replacing a hand-written document merely because one numbered heading happens to match and inserting numbered headings beside hand-written equivalents (e.g., `## Overview` alongside `## 1. Overview`). Legacy title aliases remain limited to previously generated titles, but even a complete legacy heading set requires adoption confirmation when the marker is absent.

## Standard Sections (Managed)

### Single Repo / Package Document (4-5 Sections)

```yaml
- section: "1. Overview"
- section: "2. Ownership Map"
  optional: true
  legacy_titles:
    - "2. Folder Structure"
- section: "3. Core Behaviors & Patterns"
- section: "4. Conventions"
- section: "5. Working Agreements"
```

### Monorepo Root Document (2-3 Sections)

```yaml
- section: "1. Overview"
- section: "2. Ownership Map"
  optional: true
  legacy_titles:
    - "2. Folder Structure"
- section: "3. Working Agreements"
```

`Ownership Map` is optional but managed. Generate or retain it only when repository analysis finds stable responsibility boundaries or active change routes confirmed against current code or documented contracts. Do not emit placeholder content or generic directory descriptions just to satisfy the standard section list.

Section numbers are stable update identifiers. If optional `## 2. Ownership Map` is omitted, keep later standard headings numbered as `## 3`, `## 4`, and `## 5`; do not renumber them to close the gap.

## Custom Instructions

`## Custom Instructions` is the recommended place for user-owned additions that should survive update mode. It is a non-standard section, so the parser treats it like any other custom section.

```yaml
- section: "## Custom Instructions"
  owner: User
  action: Preserve heading and body exactly as-is during update mode
```

Do not merge `## Custom Instructions` content into standard sections. Standard sections remain skill-managed and are replaced after fresh repository analysis.

## Update Workflow

### Step 1: Read Existing AGENTS.md

Parse the existing file and identify all sections by their `##` headings. Resolve the early management gate and original document type before deep analysis. Keep the original bytes for later splicing; parser line indices do not authorize newline normalization.

### Step 2: Identify Standard Sections

Match each `##` heading against the current standard section titles and documented legacy aliases for the original document type. Matches are replacement candidates until the management gate passes; all other sections are preserved as-is. With **zero** matches, stop selective updating per [Skill-Generated Files Only](#skill-generated-files-only); do not infer authorship from this result.

```yaml
- input: "## 1. Overview"
  matched: true
- input: "## 2. Folder Structure"
  matched: true
  is_legacy_standard: true
  canonical_title: "## 2. Ownership Map"
  is_optional_standard: true
  is_duplicate_standard: false
- input: "## 3. Core Behaviors & Patterns"
  matched: true
- input: "## Custom Instructions"
  matched: false (preserved exactly as-is)
- input: "## 6. API Guidelines"
  matched: false (preserved as-is)
- input: "## Security Policy"
  matched: false (preserved as-is)
```

### Step 3: Re-analyze Repository

Generate fresh content for every matched standard section:

Before reanalysis, extract decision-relevant facts from the old analysis-derived managed sections per [content_quality.md](content_quality.md). Use them as inspection leads, not authority. Reconfirm their meaning against current source or contracts and add newly discovered facts. Record each important fact as included, corrected, or excluded with an evidence-based reason. A fresh section may retain verified identifiers and meaning; the prohibition on blind body reuse does not require information loss.

Store the compact record in a temporary scratch file outside the target repository and include the applicable conditions, bypass paths, lifetime, recovery/cleanup effects, and recipient scope from direct implementing helpers. Lack of recent commits can remove an Active classification, but never justifies dropping a live migration, compatibility, or guard condition: preserve it in the relevant stable boundary or core behavior.

Before selecting rows for deep tracing, account for every old managed Stable boundary, Active route, and core flow in the coverage table, and check current documented/registered surfaces for additions. Give each row a current source-based disposition; retain its live contract even when its old Active label disappears. Selected rows must be `closed` with actual implementing source evidence before their final statements can pass the semantic audit.

- Measure LOC with `tokei` to determine character limits
- Use git history as an ownership-discovery signal when available: prefer changes since the last skill-generated `AGENTS.md` update, otherwise use roughly the last 3 months with activity-based adjustment. Run `python ./scripts/git_ownership_signals.py <target_directory>` first, passing `--anchor <commit-ish>` when an update anchor exists. The script prints compact Markdown-KV high-churn path signals; use them to choose where to inspect next. Do not read broad diffs by default.
- Rebuild analysis-derived sections (`Overview`, optional `Ownership Map`, `Core Behaviors & Patterns`, `Conventions`) from fresh repository analysis
- For `Ownership Map`, split fresh content into `Stable Ownership Boundaries` and `Active Change Routes` when both have evidence. Stable boundaries describe the durable safety boundaries that the previous single-list Ownership Map would have documented; active routes add recent history-informed change deltas confirmed against current code or documented contracts. Do not let active routes replace or filter out stable boundaries. Write Active routes as parent-linked or cross-boundary deltas, not standalone ownership summaries; do not restate the parent Stable boundary's broad owner, contract, or verification. If no meaningful delta remains after removing inherited Stable details, omit the Active route. Omit an empty subsection rather than adding placeholder text. If neither subsection has evidence, do not insert the missing section; if an existing managed `Ownership Map` or legacy `Folder Structure` section was matched, remove that managed section rather than preserving stale or invented content.
- Do not write timeline summaries such as "earlier focus" or "current focus" into `AGENTS.md`; report them to the user only when useful. A history-derived boundary can be documented only after current code or documented contracts confirm it.
- Rebuild `Working Agreements` from the current canonical rule set in `working_agreements.md`, plus discovered repository-specific response language and type-check details
- Do not reuse a standard section body from the old `AGENTS.md` after a subjective "already good" judgment

Parser outputs:

```yaml
- missing_required_standard: Required headings to insert during update mode
- missing_optional_standard: Optional headings to insert only when fresh analysis produced content
- missing_standard: Backward-compatible union of both lists; do not use it alone to decide insertion
- is_duplicate_standard: Matched current or legacy heading for a canonical section that already appeared earlier
```

### Step 4: Reassemble Document

Reconstruct the document by:

1. Preserving the file title (`# AGENTS.md`) and all preamble content except the approved marker insertion or type-transition replacement. Insert a new marker immediately before the first `##` heading; replace only the marker line during a confirmed type transition
2. For each section in the original document order:
   - **Standard section** → Replace with newly generated content. If `canonical_title` differs from the original title (for example legacy `## 2. Folder Structure`), write the canonical heading.
   - **Optional standard section with no fresh content** → Omit the heading and body entirely
   - **Duplicate standard section** (`is_duplicate_standard: true`) → Omit the heading and body; report dropped managed-section wording before writing so user-owned content can be moved to a custom section
   - **All other sections** → Keep original content unchanged
3. Insert missing required standard sections at their numbered position. Insert a missing optional standard section only when fresh analysis produced evidence-backed content for it.
4. Non-standard sections interleaved between standard sections maintain their original position

The preservation rules below keep their existing scope, with the sole preamble exception for approved marker insertion or type-transition replacement. Copy preserved ranges from the original bytes using the parser's zero-based inclusive line indices; retain CRLF/LF endings, trailing whitespace, and final-newline state within those ranges. Do not round-trip preserved text through normalized split/join operations.

For unmarked adoption, insert exactly the marker line plus the existing line-ending sequence at the byte offset of the first `##` heading. Do not add a separate blank line after the marker or rebuild the old preamble for appearance. Verify that removing only the inserted marker and its one line ending from the output preamble recovers the original preamble bytes exactly.

```yaml
reassembly_rules:
  - rule: Preserve original section order
    detail: Do not reorder sections; update in place
  - rule: Standard sections get fresh content
    detail: Full replacement of section body under the heading; never retain old managed wording because it appears aligned
  - rule: Legacy standard headings migrate to canonical headings
    detail: Replace `## 2. Folder Structure` with `## 2. Ownership Map` when the optional section has fresh content; omit it when it does not
  - rule: Optional standards are evidence-gated
    detail: Do not insert or keep `Ownership Map` without concrete current boundaries
  - rule: Duplicate standard sections are managed duplicates
    detail: If both legacy and canonical headings exist, or the canonical heading appears more than once, only the first canonical section is the replacement target; later matched duplicates are omitted and reported as dropped managed content
  - rule: Non-standard sections are untouched
    detail: Heading and all content preserved exactly
  - rule: Preserve leading content
    detail: Title and any preamble before first ## heading kept as-is
```

### Step 5: Verify Managed Replacement

Before writing, verify that managed sections were regenerated and custom sections were preserved:

After final compression, compare the assembled document against the working fact record in [content_quality.md](content_quality.md). Unexplained loss or distortion of an important verified fact fails verification. Report meaningful corrections/exclusions and reasons alongside the existing dropped-wording report. Keep the overall character limit, but allow section allocations to be redistributed; do not omit necessary conditions merely to meet an initial ratio. If important facts still cannot fit, complete a reviewable candidate and ask about scope or total limit before writing.

Point each recorded behavior to its final sentence and verify its decision-relevant fields together. Then reverse-check final claims about guards, recovery, migration, restoration, reuse, and resource ownership against the implementing helpers so an incomplete fact record cannot certify an equally incomplete summary. This audit does not change custom-section preservation or add a new generated section.

- An unmarked document has explicit adoption approval for the concrete preview. Invalid markers have not been silently repaired.
- The output has exactly one valid preamble marker with the output document type. Preamble changes are limited to the approved marker operation; the marker counts toward the existing budget.

```yaml
- check: Standard section replacement
  scope: Managed sections only
  action: Confirm each matched standard section body came from fresh generation, not from the old AGENTS.md body
- check: Stale managed wording
  scope: Managed sections only
  action: Fail verification when legacy standing work-agreement phrases remain
- check: Custom section preservation
  scope: Non-standard sections only
  action: Preserve user-owned wording exactly, even if it contains phrases that would be stale in a managed section
- check: Dropped managed-section wording reported
  scope: Managed sections only
  action: List the wording removed from managed sections so the user can relocate anything they own into a custom section before it is lost
- check: Duplicate standard sections
  scope: Managed sections only
  action: Omit duplicate matched standard sections and report their dropped bodies before writing
- check: Whole optional-section removal
  scope: Managed sections only
  action: If an existing managed `Ownership Map` or legacy `Folder Structure` section will be omitted because no current evidence supports it, report the whole-section removal and get confirmation before overwriting
- check: Character budget scope
  scope: Preamble + managed sections only
  action: Verify character_limit against the preamble plus standard sections; custom sections never count toward the limit and are never trimmed to satisfy it
```

Initial stale managed-section phrase set:

```yaml
legacy_phrases:
  - "Keep edits minimal"
  - "Minimal changes"
  - "preserve public APIs"
  - "existing plugin behavior"
  - "avoid unnecessary abstraction"
```

These phrases are regression signals only inside standard managed sections. They are allowed inside custom user sections because custom sections are user-owned and must not be rewritten.

### Step 6: Write Updated File

Replace the existing `AGENTS.md` with the reassembled content.

## Verification and Regression Signals

Managed replacement applies uniformly to all standard sections. It is not specific to `Working Agreements`; the difference is only the content source:

```yaml
standard_section_sources:
  analysis_derived:
    - "1. Overview"
    - "2. Ownership Map"
    - "3. Core Behaviors & Patterns"
    - "4. Conventions"
  canonical_rule_source:
    - section: "Working Agreements"
      source: "references/working_agreements.md"
      additions: "Discovered repository language and type-check details"
```

Known regression scenario (anonymized example from an IntelliJ plugin repository):

```yaml
- file: "<project-root>/AGENTS.md"
  parser_result: "`## 5. Working Agreements` is a standard managed section in single_repo mode"
  expected_update_behavior: "Replace the old managed Working Agreements body on the next update"
  custom_sections_preserved:
    - "## 6. User Custom"
    - "## When Extending"
    - "## Threading Rules"
```

In this scenario, the legacy bullet containing `Keep edits minimal, preserve public APIs and existing plugin behavior, and colocate new code near the feature that owns it.` must be replaced because it is inside a managed standard section. The custom sections remain byte-for-byte preserved.

## Section Matching Rules

Each `##` heading is compared against the exact current standard section titles plus the documented legacy standard titles. Only headings matching those titles are replacement candidates, and become managed only after the management gate passes; all others are preserved as-is.

```yaml
matching:
  strategy: exact_title_with_legacy_aliases
  standard_titles:
    single_repo:
      - "## 1. Overview"
      - "## 2. Ownership Map"
      - "## 3. Core Behaviors & Patterns"
      - "## 4. Conventions"
      - "## 5. Working Agreements"
    monorepo_root:
      - "## 1. Overview"
      - "## 2. Ownership Map"
      - "## 3. Working Agreements"
  legacy_standard_titles:
    single_repo:
      - title: "## 2. Folder Structure"
        canonical_title: "## 2. Ownership Map"
    monorepo_root:
      - title: "## 2. Folder Structure"
        canonical_title: "## 2. Ownership Map"
```

**Edge cases**:

In the retained examples below, zero matching headings means selective updating is unavailable, not that authorship has been established. Apply the marker/adoption gate before every managed replacement.

```yaml
- case: Modified title (e.g., "## 1. Project Overview")
  action: No match; preserved as-is
- case: Required standard section missing from existing file
  action: Insert at its defined position relative to other standard sections
- case: Optional standard section missing from existing file
  action: Insert only when fresh repository analysis produced evidence-backed content
- case: Legacy standard heading (e.g., "## 2. Folder Structure")
  action: Treat as managed; write the canonical heading if fresh content exists, otherwise omit the managed section
- case: Duplicate section headings
  action: Standard duplicates are matched as managed duplicates and omitted during reassembly; non-standard duplicates are preserved
- case: "`## ` line inside a fenced code block (``` or ~~~)"
  action: Not a section boundary; parse_sections.py tracks fences and ignores it
- case: No standard heading matches at all
  action: File is not skill-generated; do not modify (see Skill-Generated Files Only)
```

## Monorepo Update Considerations

Update mode applies to each `AGENTS.md` file independently.

```yaml
- target: Root AGENTS.md
  managed_sections: 2-3 (Overview, optional Ownership Map, Working Agreements)
  custom_sections: All others preserved
- target: Package AGENTS.md
  managed_sections: 4-5 (Overview, optional Ownership Map, Core Behaviors & Patterns, Conventions, Working Agreements)
  custom_sections: All others preserved
```

**Document type transition**:

Use the marker's original type for section classification, not the new repository type. For an unmarked file, infer or ask for its original type as described above. This prevents the old type's managed headings from being accidentally carried over as custom sections. After approval, regenerate using the new type and update/add its marker while preserving every original custom section verbatim.

```yaml
- case: Single repo converted to monorepo (or vice versa)
  action: Force full regeneration instead of update
  custom_sections: Carry over verbatim into the regenerated document, preserving their original order
  confirmation: Show the user what will change and get explicit confirmation before overwriting
  reason: Section numbering differs between document types; update mode cannot reliably match sections across types
```

Forced regeneration is not a license to drop user content: every custom section from the old file must appear unchanged in the new document, and the user must confirm the rewrite before the file is overwritten.

Update respects the same generation modes as initial generation:

```yaml
- mode: All
  behavior: Update root + all package AGENTS.md files
- mode: Root Only
  behavior: Update only root AGENTS.md
- mode: Single Package
  behavior: Update only the specified package AGENTS.md
```
