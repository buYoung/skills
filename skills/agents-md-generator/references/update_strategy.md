## Update Scope

Update mode refreshes **only** the standard sections generated by this skill. Every matched standard section is a managed replacement target: replace its body with freshly generated content even when the existing wording appears acceptable. All other content in the file is treated as user-owned and preserved exactly as-is.

User-owned additions must live in non-standard sections, preferably `## Custom Instructions`. Do not add user-owned material inside standard managed sections, because those sections are fully refreshed from repository re-analysis during update mode.

```yaml
- target: Standard sections (managed by skill)
  action: Replace body with fresh managed content
  reuse_old_body: false
- target: Custom sections (user-defined)
  action: Preserve unchanged, maintain original position
```

## Skill-Generated Files Only

Update mode applies **only** to `AGENTS.md` files previously generated by this skill. Ownership is established through section matching: at least one `##` heading must exactly match the standard set for the document type.

```yaml
- case: At least one standard heading matches
  action: Proceed with update mode
- case: Zero standard headings match (every section is custom)
  meaning: The file was authored outside this skill
  action: Do NOT modify the file; report the situation to the user and stop
  follow_up: Full regeneration only on the user's explicit request
```

This guard exists because exact-title matching cannot safely splice into an externally-authored document — inserting the numbered standard headings next to hand-written equivalents (e.g., `## Overview` alongside `## 1. Overview`) would duplicate the document instead of updating it.

## Standard Sections (Managed)

### Single Repo / Package Document (5 Sections)

```yaml
- section: "1. Overview"
- section: "2. Folder Structure"
- section: "3. Core Behaviors & Patterns"
- section: "4. Conventions"
- section: "5. Working Agreements"
```

### Monorepo Root Document (3 Sections)

```yaml
- section: "1. Overview"
- section: "2. Folder Structure"
- section: "3. Working Agreements"
```

## Custom Instructions

`## Custom Instructions` is the recommended place for user-owned additions that should survive update mode. It is a non-standard section, so the parser treats it like any other custom section.

```yaml
- section: "## Custom Instructions"
  owner: User
  action: Preserve heading and body exactly as-is during update mode
```

Do not merge `## Custom Instructions` content into standard sections. Standard sections remain skill-managed and are replaced after fresh repository analysis.

## Update Workflow

### Step 1: Read Existing AGENTS.md

Parse the existing file and identify all sections by their `##` headings.

### Step 2: Identify Standard Sections

Match each `##` heading against the standard section titles. Every matched section becomes a managed replacement target; all others are preserved as-is. If **zero** headings match, stop here per [Skill-Generated Files Only](#skill-generated-files-only) — the file is not skill-generated and must not be modified.

```yaml
- input: "## 1. Overview"
  matched: true
- input: "## 3. Core Behaviors & Patterns"
  matched: true
- input: "## Custom Instructions"
  matched: false (preserved exactly as-is)
- input: "## 6. API Guidelines"
  matched: false (preserved as-is)
- input: "## Security Policy"
  matched: false (preserved as-is)
```

### Step 3: Re-analyze Repository

Generate fresh content for every matched standard section:

- Measure LOC with `tokei` to determine character limits
- Rebuild analysis-derived sections (`Overview`, `Folder Structure`, `Core Behaviors & Patterns`, `Conventions`) from fresh repository analysis
- Rebuild `Working Agreements` from the current canonical rule set in `working_agreements.md`, plus discovered repository-specific response language and type-check details
- Do not reuse a standard section body from the old `AGENTS.md` after a subjective "already good" judgment

### Step 4: Reassemble Document

Reconstruct the document by:

1. Preserving the file title (`# AGENTS.md`) and any content before the first `##` heading
2. For each section in the original document order:
   - **Standard section** → Replace with newly generated content
   - **All other sections** → Keep original content unchanged
3. Non-standard sections interleaved between standard sections maintain their original position

```yaml
reassembly_rules:
  - rule: Preserve original section order
    detail: Do not reorder sections; update in place
  - rule: Standard sections get fresh content
    detail: Full replacement of section body under the heading; never retain old managed wording because it appears aligned
  - rule: Non-standard sections are untouched
    detail: Heading and all content preserved exactly
  - rule: Preserve leading content
    detail: Title and any preamble before first ## heading kept as-is
```

### Step 5: Verify Managed Replacement

Before writing, verify that managed sections were regenerated and custom sections were preserved:

```yaml
- check: Standard section replacement
  scope: Managed sections only
  action: Confirm each matched standard section body came from fresh generation, not from the old AGENTS.md body
- check: Stale managed wording
  scope: Managed sections only
  action: Fail verification when legacy standing work-agreement phrases remain
- check: Custom section preservation
  scope: Non-standard sections only
  action: Preserve user-owned wording exactly, even if it contains phrases that would be stale in a managed section
- check: Dropped managed-section wording reported
  scope: Managed sections only
  action: List the wording removed from managed sections so the user can relocate anything they own into a custom section before it is lost
- check: Character budget scope
  scope: Preamble + managed sections only
  action: Verify character_limit against the preamble plus standard sections; custom sections never count toward the limit and are never trimmed to satisfy it
```

Initial stale managed-section phrase set:

```yaml
legacy_phrases:
  - "Keep edits minimal"
  - "Minimal changes"
  - "preserve public APIs"
  - "existing plugin behavior"
  - "avoid unnecessary abstraction"
```

These phrases are regression signals only inside standard managed sections. They are allowed inside custom user sections because custom sections are user-owned and must not be rewritten.

### Step 6: Write Updated File

Replace the existing `AGENTS.md` with the reassembled content.

## Verification and Regression Signals

Managed replacement applies uniformly to all standard sections. It is not specific to `Working Agreements`; the difference is only the content source:

```yaml
standard_section_sources:
  analysis_derived:
    - "1. Overview"
    - "2. Folder Structure"
    - "3. Core Behaviors & Patterns"
    - "4. Conventions"
  canonical_rule_source:
    - section: "Working Agreements"
      source: "references/working_agreements.md"
      additions: "Discovered repository language and type-check details"
```

Known regression scenario (anonymized example from an IntelliJ plugin repository):

```yaml
- file: "<project-root>/AGENTS.md"
  parser_result: "`## 5. Working Agreements` is a standard managed section in single_repo mode"
  expected_update_behavior: "Replace the old managed Working Agreements body on the next update"
  custom_sections_preserved:
    - "## 6. User Custom"
    - "## When Extending"
    - "## Threading Rules"
```

In this scenario, the legacy bullet containing `Keep edits minimal, preserve public APIs and existing plugin behavior, and colocate new code near the feature that owns it.` must be replaced because it is inside a managed standard section. The custom sections remain byte-for-byte preserved.

## Section Matching Rules

Each `##` heading is compared against the exact standard section titles. Only headings that match exactly are managed; all others are preserved as-is.

```yaml
matching:
  strategy: exact_title
  standard_titles:
    single_repo:
      - "## 1. Overview"
      - "## 2. Folder Structure"
      - "## 3. Core Behaviors & Patterns"
      - "## 4. Conventions"
      - "## 5. Working Agreements"
    monorepo_root:
      - "## 1. Overview"
      - "## 2. Folder Structure"
      - "## 3. Working Agreements"
```

**Edge cases**:

```yaml
- case: Modified title (e.g., "## 1. Project Overview")
  action: No match; preserved as-is
- case: Standard section missing from existing file
  action: Insert at its defined position relative to other standard sections
- case: Duplicate section headings
  action: Only the first occurrence is matched as the standard section
- case: "`## ` line inside a fenced code block (``` or ~~~)"
  action: Not a section boundary; parse_sections.py tracks fences and ignores it
- case: No standard heading matches at all
  action: File is not skill-generated; do not modify (see Skill-Generated Files Only)
```

## Monorepo Update Considerations

Update mode applies to each `AGENTS.md` file independently.

```yaml
- target: Root AGENTS.md
  managed_sections: 3 (Overview, Folder Structure, Working Agreements)
  custom_sections: All others preserved
- target: Package AGENTS.md
  managed_sections: 5 (Overview, Folder Structure, Core Behaviors & Patterns, Conventions, Working Agreements)
  custom_sections: All others preserved
```

**Document type transition**:

```yaml
- case: Single repo converted to monorepo (or vice versa)
  action: Force full regeneration instead of update
  custom_sections: Carry over verbatim into the regenerated document, preserving their original order
  confirmation: Show the user what will change and get explicit confirmation before overwriting
  reason: Section numbering differs between document types; update mode cannot reliably match sections across types
```

Forced regeneration is not a license to drop user content: every custom section from the old file must appear unchanged in the new document, and the user must confirm the rewrite before the file is overwritten.

Update respects the same generation modes as initial generation:

```yaml
- mode: All
  behavior: Update root + all package AGENTS.md files
- mode: Root Only
  behavior: Update only root AGENTS.md
- mode: Single Package
  behavior: Update only the specified package AGENTS.md
```
