# Idempotency key 한 번에 이해하기

이 문서는 HTTP 기본 개념은 알지만 분산 시스템 경험이 없는 신규 PM과 고객지원 담당자를 위한 안내입니다. 핵심은 간단합니다. 클라이언트가 하나의 논리적 작업에 하나의 UUID를 사용하면, 같은 작업의 POST 요청이 다시 도착해도 서버가 최초 응답을 재사용하도록 요청을 식별할 수 있습니다.

## 왜 필요한가

네트워크에서는 요청을 보낸 뒤 응답이 오지 않을 수 있습니다. 예를 들어 결제 서버가 요청을 처리했지만 응답이 오는 중에 연결이 끊길 수 있습니다. 그러면 클라이언트나 사용자는 결제가 처리됐는지 알기 어렵습니다.

이때 같은 작업을 다시 보내면서 같은 idempotency key를 사용하면 서버는 이를 새 작업으로 보지 않고, 앞서 저장한 처리 결과를 돌려줍니다. 따라서 “응답을 못 받았다”는 상황과 “처리가 되지 않았다”는 상황을 구분하는 데 도움이 됩니다.

단, idempotency key가 네트워크 재시도를 자동으로 수행하는 기능은 아닙니다. 재시도 요청을 실제로 보낼지는 클라이언트 또는 이를 호출하는 애플리케이션이 결정합니다.

## Idempotency key란

Idempotency key는 POST 요청에 함께 보내는 요청 식별자입니다. 이 기능에서는 클라이언트가 논리적 작업마다 새 UUID를 생성해 키로 사용해야 합니다.

여기서 “논리적 작업”은 사용자가 의도한 하나의 처리 단위입니다. 결제 버튼을 한 번 눌러 하나의 결제를 요청했다면, 그 결제 작업에 UUID 하나를 배정합니다. 같은 작업을 다시 요청해야 할 때는 그 UUID를 유지하고, 전혀 새로운 결제 작업이라면 새 UUID를 만듭니다.

## 서버가 요청을 처리하는 방식

서버의 규칙은 다음과 같습니다.

1. 클라이언트가 POST 요청에 idempotency key를 보냅니다.
2. 서버는 최초 응답을 24시간 동안 저장합니다.
3. 같은 키와 같은 요청 본문이 다시 오면 최초 응답을 반환합니다.
4. 같은 키인데 요청 본문이 다르면 `409`를 반환합니다.

요청 본문은 결제 금액, 통화, 주문 정보처럼 POST 요청에 담긴 실제 입력값을 뜻합니다. 키만 같다고 같은 작업으로 인정되는 것이 아니라, 키와 요청 본문이 함께 일치해야 최초 응답을 재사용합니다.

## 가장 중요한 운영 원칙

### 하나의 논리적 작업에는 UUID 하나

클라이언트는 논리적 작업을 시작할 때 새 UUID를 생성하고, 그 작업의 재전송에는 같은 UUID를 사용해야 합니다.

- 같은 작업을 다시 보내는 경우: 기존 UUID 유지
- 새로운 작업을 시작하는 경우: 새 UUID 생성
- 서로 다른 작업에 같은 UUID 재사용: 금지

이 원칙을 지켜야 서버가 재전송을 같은 작업으로 판단할 수 있습니다.

### 재시도와 중복 방지는 별개의 일

idempotency key는 서버가 중복 요청을 식별하고 최초 응답을 재사용하게 하는 장치입니다. 서버가 네트워크 재시도를 자동으로 시작해 주지는 않습니다. 응답을 받지 못했을 때 다시 요청할지, 언제 다시 요청할지는 클라이언트의 재시도 로직이 담당합니다.

## 결제 버튼을 두 번 누른 세 가지 사례

### 1. 두 클릭이 같은 UUID를 사용한 경우: 중복 보호

사용자가 결제 버튼을 두 번 눌렀고, 두 POST 요청이 같은 결제 내용과 같은 UUID를 사용했다고 가정합니다.

- 첫 번째 요청: 서버가 결제를 처리하고 응답을 저장합니다.
- 두 번째 요청: 키와 요청 본문이 첫 번째 요청과 같으므로 서버가 최초 응답을 반환합니다.

이 경우 두 번째 요청은 별도의 새로운 처리로 취급되지 않습니다. 같은 논리적 결제 작업을 다시 보낸 것이므로 idempotency key로 중복 처리를 보호할 수 있습니다.

### 2. 두 클릭마다 새 UUID를 만든 경우: 중복 보호 불가

이번에는 버튼 클릭마다 새 UUID를 생성했다고 가정합니다.

- 첫 번째 클릭: UUID A로 결제 요청
- 두 번째 클릭: UUID B로 결제 요청

서버는 UUID A와 UUID B를 서로 다른 키로 봅니다. 따라서 두 요청이 같은 결제 본문이더라도, 서버 입장에서는 서로 다른 논리적 작업입니다. idempotency key만으로는 두 번째 클릭을 첫 번째 클릭의 재전송이라고 판단할 수 없으므로 중복 보호가 되지 않습니다.

### 3. 같은 UUID에 다른 요청 본문을 사용한 경우: `409`

첫 번째 요청이 UUID A와 결제 금액 10,000원으로 처리된 뒤, 두 번째 요청이 같은 UUID A를 사용하면서 결제 금액 20,000원으로 보내졌다고 가정합니다.

키는 같지만 요청 본문이 다르므로 서버는 최초 응답을 반환하지 않고 `409`를 반환합니다. 이는 같은 키를 서로 다른 작업에 재사용했거나, 동일 작업의 입력값이 바뀌었다는 충돌을 알리는 결과입니다.

## PM과 고객지원 담당자가 기억할 점

사용자가 “결제 버튼을 두 번 눌렀다”고 말했을 때는 클릭 횟수만으로 결과를 판단할 수 없습니다. 각 요청이 어떤 UUID를 사용했는지, 요청 본문이 같았는지를 함께 확인해야 합니다.

| 상황 | 키 | 요청 본문 | 서버 결과 |
| --- | --- | --- | --- |
| 같은 작업의 재전송 | 같음 | 같음 | 최초 응답 반환 |
| 새 작업으로 다시 요청 | 다름 | 같거나 다름 | 별도 키로 처리됨 |
| 키 재사용 또는 입력 변경 | 같음 | 다름 | `409` 반환 |

특히 고객에게 “idempotency key가 있으면 자동으로 다시 시도된다”고 안내하면 안 됩니다. 이 기능은 재시도를 대신하는 기능이 아니라, 클라이언트가 같은 작업을 재전송할 때 서버가 그 작업을 식별하도록 하는 기능입니다.

## 한 줄 요약

하나의 논리적 작업에 새 UUID 하나를 만들고, 그 작업을 다시 보낼 때는 같은 UUID와 같은 요청 본문을 유지하세요. 그러면 서버는 24시간 동안 저장한 최초 응답을 돌려주며, 같은 키에 다른 본문을 보내면 `409`를 반환합니다.
