# 로컬 API `DB connection failed` 장애 대응 런북

## 1. 대상과 목적

대상은 저장소 루트의 `.env`를 사용해 로컬 PostgreSQL에 연결하는 API다. 어제까지 실행되던 API가 오늘 `DB connection failed`로 시작되지 않을 때, 당직자가 상태를 보존하고 저위험 확인부터 원인을 좁혀 복구한다. 복구는 다음 두 조건을 모두 확인했을 때만 완료로 판정한다.

- 시작 로그에 정확히 `Server running on http://localhost:3000`이 표시된다.
- `GET /health`가 정확히 `{"status":"ok"}`를 반환한다.

이 문서에는 저장소에서 확인되지 않은 실행 명령을 새로 만들지 않는다. 명령을 실행해야 할 때는 해당 저장소에 이미 문서화되었거나 당직자 환경에서 승인된 시작·로그·상태 확인 명령만 사용한다.

## 2. 증상과 영향

- 증상: API 시작 과정에서 `DB connection failed`가 나타나고 정상 시작 로그가 보이지 않는다.
- 영향: API 요청을 처리할 수 없다. 데이터 변경을 유발하는 재시도나 설정 변경은 원인과 범위를 확인하기 전까지 보류한다.
- 기본 심각도: 로컬 개발 환경의 단일 API 장애. 다른 환경이나 공유 데이터베이스에 영향이 있다는 증거가 있으면 즉시 상향한다.

## 3. 즉시 안전 조치와 전제 조건

1. 현재 터미널 출력, 장애 시각, 마지막 정상 시각, 변경한 파일·환경·컨테이너 작업을 기록한다. 로그와 설정을 지우거나 덮어쓰지 않는다.
2. 저장소 루트가 맞는지 확인한다. 루트 위치를 확인할 수 없으면 시작·복구 작업을 중단하고 담당자에게 위치를 확인한다.
3. 저장소 루트에 `.env`가 존재하는지 파일 존재 여부만 확인한다. 그 내용, 비밀번호, 연결 문자열 전체는 채팅·티켓·로그에 복사하지 않는다.
4. Docker와 `postgres` 컨테이너가 정상 실행 중인지 기존 상태 화면 또는 저장소에 문서화된 읽기 전용 상태 확인 절차로 확인한다.
5. 위 전제 중 하나라도 확인되지 않으면 API 설정을 수정하거나 컨테이너를 재시작하지 않는다. 확인 결과와 중단 사유를 남기고 `상향 보고`로 이동한다.

## 4. 빠른 분류

| 관찰 결과 | 판단 | 다음 조치 |
|---|---|---|
| Docker와 `postgres`가 정상이고 루트 `.env`도 존재 | 실행 기반은 확인됨 | API가 읽는 설정과 실제 PostgreSQL 접속 대상의 불일치를 저위험으로 대조한다. |
| Docker 또는 `postgres`가 비정상 | 데이터베이스 실행 상태가 원인일 수 있음 | 먼저 현재 상태와 로그를 보존한다. 저장소에 문서화된 복구 절차가 있을 때만 그 범위 안에서 복구한다. |
| 루트 `.env`가 없음 | API가 필요한 환경 설정을 읽지 못할 수 있음 | 파일을 새로 만들거나 내용을 추측하지 말고 중단·상향한다. |
| 상태 확인 또는 로그가 서로 모순되거나 접근할 수 없음 | 관찰 근거 부족 | 추가 변경 없이 증거를 첨부해 상향한다. |

## 5. 진단 분기

### 분기 A — Docker와 `postgres`가 정상 실행 중인가

- 확인: 이미 승인된 Docker/컨테이너 상태 확인 절차를 사용한다.
- 기대 증거: Docker가 실행 중이고 `postgres` 컨테이너가 정상 상태라는 관찰 결과와 확인 시각.
- 정상일 때: 분기 B로 이동한다.
- 비정상일 때: 현재 컨테이너 상태와 관련 로그를 먼저 저장한다. 저장소 런북에 명시된 범위의 재시작·복구 절차가 없거나, 데이터 삭제·볼륨 초기화·강제 재생성이 필요한 경우 중단하고 상향한다.

### 분기 B — `.env`와 API 실행 설정의 연결 대상이 일치하는가

- 확인: 저장소의 문서와 기존 설정 로더가 요구하는 항목·키 이름을 기준으로 `.env`의 키 존재 여부와 형식만 대조한다. 비밀 값은 출력하지 않는다.
- 기대 증거: 필요한 키가 존재하고, API가 기대하는 호스트·포트·데이터베이스 대상이 PostgreSQL 컨테이너의 문서화된 접속 대상과 일치한다는 확인.
- 일치할 때: 분기 C로 이동한다. 이 사실만으로 접속 성공을 가정하지 않는다.
- 누락·불일치일 때: 값을 추측하거나 공유 설정을 덮어쓰지 않는다. 승인된 최신 설정 원본과 변경 이력을 확인할 수 있으면 담당자와 대조하고, 원본이 없으면 상향한다.

### 분기 C — PostgreSQL 로그에 접속 거부·준비 지연·인증 오류가 있는가

- 확인: 기존 승인 절차로 API 시작 직전의 PostgreSQL과 API 로그를 읽는다.
- 기대 증거: 오류 유형, 최초 발생 시각, 영향받은 컨테이너 또는 프로세스가 서로 맞아야 한다.
- 준비 지연 또는 일시적 상태가 명확하고 저장소 절차가 재시도를 허용할 때: 그 절차의 제한된 재시도만 수행한 뒤 분기 D로 이동한다.
- 인증·대상·권한 오류가 명확하거나 로그가 민감정보를 노출할 우려가 있을 때: 설정을 임의 변경하지 말고 증거를 마스킹해 상향한다.
- 원인이 명확하지 않거나 로그가 부족할 때: 반복 재시도하지 말고 분기 D를 한 번 시도한 뒤 상향한다.

## 6. 복구 절차

1. **증거 보존** — 위험도 낮음. 현재 API·PostgreSQL 로그, 컨테이너 상태, 확인 시각, 마지막 정상 시각을 저장한다. 기대 변화는 이후 조치 전후를 비교할 수 있는 기록이 생기는 것이다. 로그 보존 자체가 실패하면 복구를 진행하지 않고 상향한다.
2. **문서화된 설정 복구** — 위험도 중간. 분기 B에서 누락 또는 변경이 확인되고 승인된 원본이 있는 경우에만, 그 원본과 저장소의 기존 설정 변경 절차에 따라 `.env`를 복구한다. 비밀 값은 화면에 출력하지 않는다. 변경 전 파일을 안전한 승인 위치에 보존하고, 원본이 없거나 대상이 불명확하면 중단한다.
3. **문서화된 서비스 재시작 또는 제한된 재시도** — 위험도 중간. 설정을 읽는 시작 절차가 저장소 문서에 명시된 경우에만 실행한다. `restart everything`, 볼륨 삭제, 데이터베이스 초기화, 강제 재생성은 수행하지 않는다. 기대 변화는 API가 새 설정을 읽고 DB 연결을 다시 시도하는 것이다.
4. 각 조치 뒤에는 즉시 분기 D의 검증을 수행한다. 기대 결과가 나오지 않으면 같은 조치를 반복하지 말고 롤백 또는 상향 기준을 적용한다.

## 7. 복구 확인

복구 성공은 부분적인 컨테이너 상태가 아니라 사용자 관찰 결과로 확인한다.

1. API 시작 출력에 `Server running on http://localhost:3000`이 정확히 나타나는지 확인한다.
2. 승인된 HTTP 확인 절차로 `GET /health`를 호출한다.
3. 응답 본문이 정확히 `{"status":"ok"}`인지 확인한다. 상태 코드가 문서화되어 있다면 함께 기록하되, 확인되지 않은 상태 코드를 성공 조건으로 만들지 않는다.
4. 두 조건 중 하나라도 없거나 다른 값이면 복구 완료로 표시하지 않는다. 직전 조치와 로그를 보존하고 원인 불명으로 상향한다.

## 8. 롤백과 중단 조건

- 설정 변경을 했다면 변경 전 보존본과 승인된 원본의 차이를 확인한 뒤, 저장소에 문서화된 롤백 절차로만 되돌린다. 원본 경로·대상이 확실하지 않으면 덮어쓰지 않는다.
- 다음 상황에서는 즉시 중단한다: `.env` 부재, Docker 또는 `postgres` 상태 미확인, 데이터 삭제·볼륨 초기화가 필요한 조치, 민감정보 노출 위험, 반복 재시도에도 동일 실패, 로그·상태 확인 불가, 정상 시작 로그와 `/health` 응답을 모두 확인하지 못함.
- 중단은 실패 은폐가 아니다. 수행한 마지막 안전 조치까지만 기록하고 상향 보고한다.

## 9. 상향 보고 기준과 첨부 증거

다음 중 하나면 애플리케이션·데이터베이스 담당자에게 상향한다.

- 필수 전제(`Docker`, `postgres`, 루트 `.env`)를 확인할 수 없음
- 승인된 설정 원본 또는 저장소 문서화 절차가 없음
- 인증·권한·접속 대상 오류가 확인됨
- 복구 조치 후에도 시작 로그 또는 `GET /health` 성공 조건이 충족되지 않음
- 데이터 손실·공유 환경 영향·민감정보 노출 가능성이 있음

보고서에는 다음을 첨부한다.

- 장애 최초 관찰 시각과 마지막 정상 시각
- 저장소 루트 확인 결과와 `.env` 존재 여부(값은 제외)
- Docker 및 `postgres` 상태와 확인 시각
- API와 PostgreSQL의 관련 로그 구간(비밀번호·토큰·전체 연결 문자열 마스킹)
- 수행한 조치, 각 조치의 시각, 조치 전후 결과
- 설정 키 이름 및 기대 대상과의 일치 여부(실제 비밀 값 제외)
- `Server running on http://localhost:3000` 표시 여부
- `GET /health` 응답 원문과 확인 시각
- 아직 확인하지 못한 사항, 중단한 이유, 필요한 담당자 판단

## 10. 사후 조치

서비스가 정상화된 뒤에만 원인 확정, 설정 변경 이력 보강, 로그 보존 기간 점검, 재현 가능한 검증 절차 문서화를 별도 작업으로 진행한다. 활성 장애 중에는 예방 작업을 위해 설정·컨테이너 구성을 추가로 바꾸지 않는다.
