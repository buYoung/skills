# Saved Search Filters v1.0

## 1. Document Intent

이 문서는 관리자 웹 대시보드의 Saved Search Filters v1.0이 무엇을 제공하고 어떤 정책으로 동작하는지 정의하는 현재 결정 원본이다. 구현자와 검토자는 이 문서를 기준으로 저장, 적용, 수정, 삭제, 권한, 부분 적용의 일관된 동작을 판단한다.

## 2. Background / Problem

반복적으로 같은 사용자 검색을 수행하는 워크스페이스 관리자는 현재 매번 필터 조합을 다시 설정해야 한다. 이 반복 작업은 검색 시간을 늘리고, 같은 조건을 다시 입력하는 과정에서 설정 누락이나 오입력 가능성을 만든다.

해결하려는 문제는 현재 필터 조합을 이름 있는 재사용 항목으로 보존하고, 이후 목록에서 빠르게 적용할 수 있게 하는 것이다. 저장된 조건의 기반 필드가 나중에 제거되더라도 검색 자체가 중단되지 않고 적용 가능한 조건만 사용해야 한다.

## 3. Feature Definition

Saved Search Filters는 관리자가 현재 사용자 검색 필터 조합을 이름과 함께 저장하고, 자신이 저장한 항목을 목록에서 적용·이름 변경·삭제하는 기능이다.

저장 데이터는 사용자와 워크스페이스의 조합에 귀속된다. 한 조합에는 최대 20개의 필터만 존재하며, 이름은 해당 사용자·워크스페이스 범위에서 대소문자를 구분하지 않고 고유해야 한다. 저장된 필터는 검색 필드, 연산자, 검색값만 보존하며 개인정보 원문을 별도로 저장하지 않는다.

필터를 적용할 때 현재 시스템에 존재하지 않는 조건 필드는 제외하고 유효한 조건만 검색에 반영한다. 하나라도 제외되면 사용자에게 부분 적용 안내를 표시한다.

## 4. Goals & Non-Goals

### 목표

- 반복 검색을 이름 있는 저장 항목으로 재사용하게 한다.
- 저장된 필터를 목록에서 적용·이름 변경·삭제할 수 있게 한다.
- 사용자·워크스페이스 소유권과 최대 20개 제한을 일관되게 보장한다.
- 필드 제거 이후에도 유효한 조건으로 안전하게 부분 적용한다.
- 저장·적용·부분 적용·삭제 결과를 관측 가능하게 한다.
- 키보드만으로 목록 작업을 완료할 수 있게 하고 유니코드 및 번역을 지원한다.

### 비목표

- v1.0에서 필터를 다른 사용자와 공유하지 않는다.
- 저장 필터를 기본 필터로 지정하지 않는다.
- 사용자가 저장 목록의 정렬 방식을 지정하지 않는다.
- localStorage에 저장하지 않는다. 여러 기기에서 사용할 수 없기 때문이다.
- 워크스페이스 전체 공유 방식은 제공하지 않는다. 권한과 소유권 복잡성이 크기 때문이다.

## 5. User Model & Core Concepts

주 사용자는 워크스페이스의 사용자 검색을 반복 수행하는 워크스페이스 관리자다. 기능 사용자는 기존 관리자 인증을 통과한 관리자이며, 자신이 현재 선택한 워크스페이스 안에서 생성한 저장 필터만 볼 수 있다.

핵심 개념은 다음과 같다.

- 저장 필터: 이름과 필터 조건 집합을 가진 사용자 소유의 재사용 항목.
- 필터 조건: 검색 필드, 연산자, 검색값의 조합. 검색값은 기능에 필요한 값만 저장한다.
- 소유 범위: 사용자 식별자와 워크스페이스 식별자의 조합. 목록 조회와 모든 변경은 이 범위에 귀속된다.
- 유효 조건: 적용 시점에 현재 검색 시스템이 인식하고 지원하는 필드와 연산자를 가진 조건.
- 부분 적용: 저장된 조건 중 유효 조건만 사용하고 제외된 조건이 있음을 안내하는 결과.

이름 비교는 대소문자를 구분하지 않는다. 따라서 `My Users`와 `my users`는 같은 이름으로 취급되며, 유니코드 이름도 동일한 비교 규칙의 적용 대상이다.

## 6. Relationship to Existing Features

이 기능은 기존 관리자 인증, 워크스페이스 선택, 사용자 검색 필터, 검색 결과 화면을 확장한다. 검색 화면의 현재 필터 조합을 저장 대상으로 삼고, 저장 목록에서 선택한 조건을 기존 검색 필터 입력과 검색 실행 흐름에 전달한다.

인증과 워크스페이스 문맥은 기존 기능을 사용한다. Saved Search Filters는 별도의 로그인 체계나 워크스페이스 전체 공유 권한 모델을 도입하지 않는다.

## 7. Primary User Flows

### 필터 저장

1. 관리자가 사용자 검색 화면에서 조건을 설정한다.
2. 저장 동작을 선택하고 이름을 입력한다.
3. 시스템은 현재 관리자와 워크스페이스 범위, 이름의 공백·유니코드 표현, 대소문자 비구분 고유성, 기존 저장 개수 20개 제한을 검사한다.
4. 검사를 통과하면 조건의 필드·연산자·검색값과 이름을 서버에 저장한다.
5. 성공 결과를 표시하고 목록에 새 항목을 반영한다.

이름이 중복되거나 20개를 초과하면 저장하지 않고 원인을 안내한다. 서버가 최종 고유성과 개수 제한을 보장하며, 동시 저장으로 인한 경쟁 상황도 실패 결과로 명확히 표시한다.

### 저장 필터 적용

1. 관리자가 자신의 저장 필터 목록에서 항목을 선택한다.
2. 시스템은 현재 관리자와 워크스페이스 소유권을 확인한다.
3. 저장된 각 조건을 현재 지원 필드와 비교한다.
4. 모든 조건이 유효하면 전체 조건을 검색 화면에 적용한다.
5. 일부 조건만 유효하면 유효 조건만 적용하고, 제외된 조건 수 또는 조건 식별이 가능한 안내를 표시한다.
6. 유효 조건이 하나도 없으면 빈 조건으로 검색하며, 적용할 수 있는 조건이 없다는 안내를 표시한다.

### 이름 변경

관리자가 자신의 항목에서 이름 변경을 선택하면 새 이름을 입력한다. 시스템은 같은 소유 범위에서 대소문자를 구분하지 않는 중복 여부를 확인하고, 성공한 경우 목록의 이름을 갱신한다. 다른 항목과 중복되거나 변경 대상이 소유 범위 밖에 있으면 기존 이름을 유지하고 실패 이유를 안내한다.

### 삭제

관리자가 자신의 항목에서 삭제를 선택하면 삭제 대상과 결과를 확인할 수 있는 확인 단계를 거친다. 확인 후 소유권을 다시 검사하고 성공하면 서버에서 삭제하며 목록에서 제거한다. 취소하거나 실패하면 항목을 유지하고 그 결과를 알린다.

## 8. Design

### 저장 모델

각 저장 필터는 사용자 식별자와 워크스페이스 식별자, 표시 이름, 필터 조건 목록, 생성·수정 시점을 가진다. 조건 목록의 각 원소는 검색 필드, 연산자, 검색값으로 구성한다. 개인정보 원문이나 검색 결과 스냅샷은 저장하지 않는다.

서버 영속 저장소를 단일 원천으로 사용한다. 목록 조회 시 현재 인증 주체와 현재 워크스페이스를 함께 사용해 소유 범위를 제한하며, 클라이언트가 전달한 소유자 정보는 권한 판단의 근거로 신뢰하지 않는다.

### 목록과 상호작용

목록은 각 저장 필터의 이름과 적용·이름 변경·삭제 동작을 명확히 구분해 제공한다. 빈 목록에는 저장 방법과 현재 제한을 설명하는 안내를 표시한다. 20개에 도달하면 추가 저장 동작을 비활성화하거나 제한 사유를 안내하되, 기존 항목의 적용·이름 변경·삭제는 계속 가능해야 한다.

모든 목록 동작은 포인터 없이 키보드로 탐색, 선택, 실행, 취소할 수 있어야 한다. 현재 포커스와 성공·실패·부분 적용 상태를 화면 낭독기가 이해할 수 있는 방식으로 전달한다.

### 이름 처리

표시 이름은 사용자가 입력한 유니코드 문자를 지원한다. 고유성 검사는 저장 및 이름 변경 시 서버에서 대소문자를 구분하지 않는 방식으로 수행한다. 검사의 표현 정규화 방식은 저장된 표시 이름을 불필요하게 바꾸지 않으면서 동일 이름 충돌을 놓치지 않아야 한다.

### 적용 결과

적용은 저장 데이터를 현재 검색 기능의 조건 표현으로 변환한다. 지원되지 않거나 제거된 필드가 포함된 조건은 검색 요청에 넣지 않는다. 부분 적용 여부와 제외된 조건 정보는 사용자에게 안내하고 관측 이벤트에도 결과 유형으로 남긴다.

## 9. Policy Decisions

- 저장 범위는 사용자·워크스페이스 조합으로 고정한다. 소유자는 자신이 저장한 항목만 조회·변경할 수 있다.
- 저장 개수의 상한은 소유 범위당 20개다. 초과 저장은 거부한다.
- 이름 고유성은 소유 범위 안에서 대소문자를 구분하지 않는다. 중복 저장과 중복 이름 변경은 거부한다.
- 인증은 기존 관리자 인증을 사용한다. 조회·저장·적용에 따른 조회·이름 변경·삭제의 모든 요청에서 소유권을 검사한다.
- 저장하는 정보는 필드, 연산자, 검색값뿐이며 개인정보 원문은 저장하지 않는다.
- 필드가 제거된 뒤의 적용은 유효 조건만 사용한다. 일부 또는 전체 조건이 제외되면 안내를 표시한다.
- v1.0에는 공유 필터, 기본 필터 지정, 사용자 지정 정렬을 포함하지 않는다.
- localStorage와 워크스페이스 공유 저장은 각각 다중 기기 사용 한계와 권한·소유권 복잡성 때문에 채택하지 않는다.

## 10. Alternatives Considered

### localStorage 저장

브라우저별로 간단히 구현할 수 있지만 여러 기기에서 동일 저장 필터를 사용할 수 없다. 관리자 기능의 사용 맥락과 맞지 않아 제외한다.

### 워크스페이스 공유 저장

한 번 저장한 필터를 여러 사용자가 쓸 수 있지만, 공유 대상과 변경 권한, 삭제 권한, 소유권 이전을 정의해야 한다. v1.0의 개인 재사용 문제에 비해 권한 복잡성이 커서 제외한다.

### 사용자별 제한 없는 서버 저장

서버 저장은 채택하지만 개수 제한을 두지 않는 선택은 목록 관리성과 저장 자원 예측을 어렵게 한다. 소유 범위당 20개 제한을 두는 현재 결정을 유지한다.

### 필드가 제거된 저장 필터를 전부 실패 처리

조건 하나가 사라졌다는 이유로 나머지 유효 조건까지 사용할 수 없게 된다. 검색 연속성을 위해 유효 조건을 적용하고 부분 적용을 안내하는 방식을 채택한다.

## 11. Cross-cutting Concerns

### 11.1 Security

기존 관리자 인증을 통과한 요청만 처리한다. 서버는 조회와 모든 변경에서 인증 주체의 사용자 식별자 및 현재 워크스페이스를 기준으로 소유권을 검사하고, 클라이언트가 지정한 소유자·워크스페이스 값으로 이를 우회할 수 없게 한다. 실패 응답은 다른 사용자의 필터 존재 여부를 추측할 수 있는 정보를 노출하지 않는다.

### 11.2 Privacy

저장 데이터에는 검색 필드, 연산자, 검색값만 포함한다. 개인정보 원문이나 검색 결과는 저장하지 않는다. 화면과 관측 데이터에서도 검색값을 불필요하게 원문으로 남기지 않으며, 저장·조회·삭제 수명은 기존 서버 데이터 보존 정책을 따른다.

### 11.3 Permissions

권한 주체는 기존 워크스페이스 관리자다. 필터는 워크스페이스에 속하지만 소유자는 개별 사용자이며, 공유·양도·관리자 간 대리 변경은 v1.0에서 허용하지 않는다. 목록 조회, 적용 데이터 조회, 이름 변경, 삭제 각각에서 소유권을 확인한다.

### 11.4 Observability

저장 성공·실패, 적용 성공, 부분 적용, 삭제 성공·실패를 결과 유형별로 관측할 수 있어야 한다. 이벤트에는 워크스페이스와 사용자 범위, 결과 유형, 조건 개수, 제외된 조건 개수, 실패 분류 등 운영에 필요한 최소 메타데이터를 포함하되 검색값과 개인정보 원문은 포함하지 않는다. 중복 이름, 개수 제한, 권한 거부, 유효 조건 없음은 서로 구분한다.

### 11.5 Accessibility

목록 탐색과 적용·이름 변경·삭제를 키보드만으로 완료할 수 있어야 한다. 포커스 순서와 현재 선택 항목을 명확히 하고, 확인 대화와 결과 안내를 키보드로 닫거나 재시도할 수 있게 한다. 성공, 실패, 부분 적용 안내는 시각적 표시만으로 전달하지 않는다.

### 11.6 Internationalization

필터 이름과 안내 문구는 유니코드와 번역을 지원한다. 문구는 하드코딩된 언어별 문자열에 의존하지 않고 결과 유형과 변수(예: 제외된 조건 수)를 번역 가능한 메시지로 표현한다. 대소문자를 구분하지 않는 이름 비교는 지원하는 유니코드 이름에서 일관되게 적용하고, 표시 이름의 원래 표현은 보존한다.

## 12. Scope

### 포함

- 관리자 웹 대시보드의 현재 사용자 검색 필터를 서버에 저장
- 사용자·워크스페이스별 최대 20개 목록 조회
- 저장 필터 적용, 이름 변경, 삭제
- 대소문자 비구분 이름 중복 거부
- 소유권 검사와 기존 관리자 인증 연계
- 필드 제거 시 유효 조건만 적용하는 부분 적용 및 안내
- 결과 관측, 키보드 접근성, 유니코드·번역 지원

### 제외

- 사용자 간 또는 워크스페이스 전체 필터 공유
- 기본 필터 지정
- 사용자 지정 정렬
- localStorage 기반 저장
- 개인정보 원문 또는 검색 결과 저장

## 13. Risks & Open Questions

### 위험

- 검색 필드나 연산자 체계가 변경될 때 저장 조건의 유효성 판단이 누락될 수 있다. 적용 시점에 현재 지원 목록과 대조하고 부분 적용 결과를 관측해야 한다.
- 유니코드 대소문자 비교가 저장소와 화면에서 다르게 처리되면 중복 이름이 생길 수 있다. 서버의 단일 비교 규칙과 충돌 결과를 기준으로 삼아야 한다.
- 동시 요청이 20개 제한이나 이름 고유성을 각각 통과할 수 있다. 최종 저장 경계에서 두 정책을 원자적으로 보장해야 한다.
- 관측 데이터가 검색값을 포함하면 개인정보 노출 위험이 생긴다. 이벤트 필드를 최소화하고 검색값을 기록하지 않는다.

### 열어 둔 질문

- 이름의 앞뒤 공백을 고유성 비교에서 제거할지 여부는 제품의 입력 규칙 결정이 필요하다. 결정 전까지는 표시 이름을 보존하고 동일한 비교 규칙을 저장과 변경에 일관되게 적용한다.
- 저장 필터 적용 후 자동 검색을 실행할지, 조건만 채우고 관리자가 검색을 실행할지는 기존 검색 화면의 현재 실행 모델과 맞춰 확정해야 한다.
- 저장된 연산자가 더 이상 지원되지 않을 때 사용자 안내에서 필드명과 연산자명을 어느 수준까지 노출할지는 번역 및 접근성 문구 검토가 필요하다.
