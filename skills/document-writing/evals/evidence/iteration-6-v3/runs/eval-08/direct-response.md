# 로컬 API `DB connection failed` 장애 대응 런북

## 1. 목적과 적용 범위

이 런북은 어제까지 실행되던 로컬 API가 오늘 `DB connection failed`로 시작되지 않을 때 당직자가 안전하게 상태를 확인하고, 원인을 좁혀 복구를 시도한 뒤 검증하거나 상향 보고하기 위한 절차다.

이 문서에는 제공된 환경 정보만 반영한다. 구체적인 셸 명령, 서비스 이름, 데이터베이스 접속값, 로그 수집 도구가 제공되지 않았으므로 이를 추측해 새로 만들지 않는다. 아래의 “확인”은 저장소와 운영 환경에 이미 정해진 Docker·API 실행 및 로그 확인 방법으로 수행한다.

## 2. 증상과 영향

- 증상: API가 시작되지 않고 `DB connection failed`가 나타난다.
- 영향: API 요청을 처리할 수 없다.
- 정상 복구의 기준:
  - `Server running on http://localhost:3000` 로그가 보인다.
  - `GET /health`가 `{"status":"ok"}`를 반환한다.

## 3. 안전 원칙과 중단 기준

먼저 읽기 전용 상태와 로그를 확인한다. 데이터 삭제, 볼륨 초기화, 스키마 변경, 자격 증명 노출, 모든 컨테이너 일괄 재시작은 이 런북의 범위가 아니며 수행하지 않는다.

다음 중 하나라도 해당하면 복구 조작을 중단하고 상향 보고한다.

- Docker 또는 `postgres` 컨테이너가 정상 실행 중이라는 사실을 확인할 수 없다.
- 저장소 루트에 `.env`가 없거나, 읽을 수 없거나, 어느 값이 올바른지 확인할 근거가 없다.
- 로그에서 데이터 손실·볼륨 손상·인증 실패의 범위를 판단할 수 없다.
- 기존 실행 절차에 없는 명령이나 대상(컨테이너, 볼륨, 프로세스)을 특정해야만 다음 단계로 갈 수 있다.
- 복구 조작 후 성공 기준을 모두 확인하지 못했다.

## 4. 초기 안전 확인

다음 항목을 순서대로 확인하고, 각 결과와 시각을 기록한다.

| 확인 항목 | 기대되는 관찰 결과 | 기대와 다를 때 |
|---|---|---|
| Docker 상태 | Docker가 정상 실행 중 | API나 컨테이너를 재시작하지 말고 상향 보고 |
| `postgres` 컨테이너 | 컨테이너가 정상 실행 중 | 아래 진단을 진행하지 말고 상향 보고 |
| 저장소 위치 | API를 실행하는 저장소 루트가 식별됨 | 정확한 저장소 루트를 확인할 수 없으면 중단 |
| 환경 파일 | 저장소 루트에 `.env`가 존재함 | 중단 후 상향 보고; 비밀값을 보고서에 첨부하지 않음 |

`Docker 정상`과 `postgres 정상 실행 중`은 추정하지 말고 현재 상태 화면 또는 기존 운영 점검 결과로 확인한다. 어느 한 항목이라도 확인되지 않으면 “정상”으로 간주하지 않는다.

## 5. 진단 분기

### 분기 A — Docker 또는 `postgres`가 정상 실행 중이 아닌 경우

1. 관찰: Docker가 중지되었거나 `postgres` 컨테이너가 실행 중이 아니거나 정상 상태를 확인할 수 없다.
2. 확인: 기존 Docker 운영 절차에 따라 상태와 관련 로그를 확인한다.
3. 기대 증거: 중지·비정상 상태, 마지막 상태 변화 시각, 오류 로그가 확인된다.
4. 다음 조치: 컨테이너 재생성, 볼륨 조작, 데이터베이스 복구는 승인된 절차와 담당자가 필요하므로 당직자는 중단하고 상향 보고한다.
5. 중단 조건: 데이터 디렉터리나 볼륨에 쓰기 조작이 필요하거나 원인을 확정할 수 없으면 즉시 중단한다.

### 분기 B — Docker와 `postgres`는 정상인데 `.env`가 없는 경우

1. 관찰: 두 컨테이너는 정상이나 저장소 루트에 `.env`가 없다.
2. 확인: `.env`가 실제로 다른 경로에 있는지, 또는 기존 배포·실행 절차가 별도 환경 주입을 명시하는지 확인한다.
3. 기대 증거: 승인된 환경 주입 경로 또는 파일 부재가 확인된다.
4. 다음 조치: 승인된 원본에서 `.env`를 복원할 수 있고 값의 정확성을 확인할 수 있을 때만 기존 절차로 복원한다. 그런 근거가 없으면 중단하고 상향 보고한다.
5. 중단 조건: 비밀번호·토큰을 채팅, 로그, 보고서에 복사해야 하거나 출처가 불명확한 값을 넣어야 하면 중단한다.

### 분기 C — Docker, `postgres`, `.env`가 모두 확인되는 경우

1. 관찰: 세 가지 전제 조건이 모두 충족된다.
2. 확인: 기존 API 실행 절차의 시작 로그에서 `DB connection failed`의 상세 원인(예: 연결 대상, 인증, 타임아웃)을 확인한다. 상세 로그가 없으면 그 사실 자체를 기록한다.
3. 기대 증거: 실패 시각, 오류 전문, API가 참조한 설정의 출처가 확인된다. 비밀값 자체는 기록하지 않는다.
4. 다음 조치:
   - 설정 파일의 키 이름이나 연결 대상이 최근 변경되었다는 근거가 있으면, 승인된 원본과 비교한다.
   - 잘못된 값이 확인되고 승인된 값이 있으면 해당 값만 최소 범위로 복원한 뒤 API만 기존 절차로 다시 시작한다.
   - 설정 이상 근거가 없으면 반복 재시작하지 말고 오류 전문과 시각을 첨부해 상향 보고한다.
5. 중단 조건: 값의 정합성을 확인할 수 없거나, 데이터베이스 자체를 재시작·초기화해야 하거나, 재시작이 데이터에 영향을 줄 수 있으면 중단한다.

## 6. 복구 절차

복구 조작은 진단 결과가 명확하고 승인된 기존 절차가 있을 때만 수행한다.

1. 변경 전 현재 상태, 오류 로그, `.env`의 존재 여부를 기록한다. 비밀값은 기록하지 않는다.
2. 확인된 설정 오류가 있으면 변경 범위를 해당 설정 항목으로 제한하고, 승인된 원본을 사용한다.
3. API만 기존 실행 절차로 다시 시작한다. “모든 컨테이너 재시작”이나 `postgres` 볼륨 삭제·초기화는 수행하지 않는다.
4. 시작 과정에서 새로운 오류가 발생하거나 같은 오류가 반복되면 재시작을 반복하지 않고 중단 기준에 따라 상향 보고한다.

## 7. 복구 검증

복구 완료라고 보고하려면 다음 두 결과를 모두 관찰해야 한다.

- API 로그에 정확히 `Server running on http://localhost:3000`가 표시된다.
- `GET /health` 요청이 정확히 `{"status":"ok"}` 응답을 반환한다.

두 결과 중 하나라도 없으면 복구 미확정이다. 로그만 보이고 `/health`가 실패하거나, `/health`가 성공해도 시작 로그가 없으면 성공으로 보고하지 않는다. 검증 시각과 확인한 로그·응답을 기록하되, 자격 증명과 비밀값은 제외한다.

## 8. 롤백

설정 변경으로 증상이 악화되거나 검증에 실패하면 변경한 설정만 변경 전의 승인된 값으로 되돌린다. 변경 전 값의 출처를 확인할 수 없거나 롤백에 데이터베이스·볼륨 조작이 필요하면 직접 롤백하지 말고 상향 보고한다. 롤백 후에도 위의 두 복구 기준을 다시 확인한다.

## 9. 상향 보고 기준과 첨부 증거

다음 경우 담당자에게 상향 보고한다.

- Docker 또는 `postgres`의 정상 상태를 확인할 수 없음
- `.env` 부재 또는 환경값 출처·정합성 불명
- 오류 원인을 특정할 수 없음
- 승인된 기존 복구 절차가 없음
- 복구 후 두 검증 기준을 모두 충족하지 못함
- 데이터 손실, 볼륨 손상, 인증 정보 노출, 서비스 영향 확대 가능성이 있음

보고에는 다음을 포함한다.

- 장애 시작 추정 시각과 마지막 정상 시각(알 수 없으면 “미확인”)
- 저장소 루트 식별 결과와 `.env` 존재 여부(값은 제외)
- Docker와 `postgres`의 관찰된 상태 및 확인 시각
- `DB connection failed`를 포함한 관련 로그 전문과 시각
- 수행한 변경, 재시작 여부, 변경 전후의 관찰 결과
- `Server running on http://localhost:3000` 로그 확인 여부
- `GET /health`의 실제 응답과 확인 시각
- 아직 확인하지 못한 항목과 당직자가 중단한 이유

## 10. 후속 조치

복구 또는 상향 보고 후에는 이번 장애의 원인, `.env` 공급 방식, Docker와 `postgres` 상태를 확인할 수 있는 기존 점검 절차, API 시작 로그 및 `/health` 검증 방법을 담당자가 문서화해야 한다. 이 정보가 추가로 승인되기 전까지는 이 런북에 새로운 명령이나 복구 방법을 추측해 추가하지 않는다.
