# Idempotency key 한 번에 이해하기

이 문서의 독자는 HTTP 기본 개념은 알지만 분산 시스템 경험이 많지 않은 신규 PM과 고객지원 담당자입니다. 핵심은 간단합니다. `idempotency key`는 네트워크 재시도 때문에 같은 결제가 두 번 처리되는 일을 막기 위해, 하나의 논리적 작업에 붙이는 고유한 식별자입니다.

## 왜 필요한가

클라이언트가 `POST` 요청을 보낸 뒤 응답을 받지 못할 수 있습니다. 예를 들어 서버가 결제를 처리했지만 응답이 네트워크에서 유실되면, 클라이언트는 결제가 실패했는지 알 수 없습니다. 이때 같은 작업을 다시 보내면 결제가 중복 처리될 수 있습니다.

Idempotency key를 사용하면 클라이언트가 같은 논리적 작업을 다시 요청했는지 서버가 판단할 수 있습니다. 다만 이 기능은 네트워크 재시도를 자동으로 수행하지 않습니다. 재시도 여부와 시점은 클라이언트 또는 호출하는 애플리케이션이 결정합니다.

## 동작 방식

클라이언트는 `POST` 요청에 키를 함께 보냅니다. 서버는 키와 최초 요청의 결과를 24시간 동안 저장하고, 이후 같은 키로 들어오는 요청을 최초 요청과 비교합니다.

| 요청 조건 | 서버의 동작 |
| --- | --- |
| 처음 보는 키 | 요청을 처리하고 최초 응답을 저장합니다. |
| 같은 키 + 같은 요청 본문 | 새로 처리하지 않고 최초 응답을 반환합니다. |
| 같은 키 + 다른 요청 본문 | 요청이 서로 충돌하므로 `409`를 반환합니다. |

여기서 “같은 작업”은 사용자가 버튼을 누른 횟수가 아니라, 클라이언트가 정의한 하나의 논리적 작업을 뜻합니다. 따라서 클라이언트는 논리적 작업마다 새 UUID를 생성해야 합니다.

## 결제 버튼을 두 번 누른 경우

### 1. 두 클릭이 같은 작업이고 같은 UUID를 사용한 경우

첫 번째 클릭이 결제 요청을 보내며 UUID `A`를 사용했다고 가정합니다. 사용자가 결과를 보지 못해 버튼을 다시 눌렀지만, 두 번째 요청에도 UUID `A`와 같은 요청 본문을 사용하면 서버는 두 번째 결제를 새로 처리하지 않습니다. 첫 번째 요청의 응답을 다시 반환합니다.

이 경우 같은 UUID가 “중복 클릭”이 아니라 “같은 결제 작업에 대한 재요청”임을 나타내므로 중복 처리를 보호합니다.

### 2. 클릭마다 새 UUID를 만든 경우

첫 번째 클릭에 UUID `A`, 두 번째 클릭에 UUID `B`를 사용하면 서버는 이를 서로 다른 논리적 작업으로 봅니다. 요청 본문이 같아도 두 요청은 각각 새 요청으로 처리될 수 있습니다. 따라서 결제가 중복될 수 있으며, 클릭마다 새 UUID를 만드는 방식은 두 번의 클릭을 하나의 작업으로 묶어 보호하지 못합니다.

새 UUID는 실제로 새로운 논리적 작업을 시작할 때 만들어야 합니다. 단순한 네트워크 재시도나 같은 작업의 재전송에는 기존 UUID를 유지해야 합니다.

### 3. 같은 UUID지만 요청 본문이 달라진 경우

첫 번째 요청이 UUID `A`와 금액 10,000원의 본문으로 처리된 뒤, 두 번째 요청이 같은 UUID `A`를 사용하면서 금액 20,000원처럼 다른 본문을 보내면 서버는 `409`를 반환합니다.

이는 서버가 UUID `A`를 이미 다른 요청 본문과 연결했기 때문입니다. 두 번째 요청의 본문을 조용히 첫 번째 본문으로 바꾸거나 새 결제로 처리하지 않습니다. 고객지원에서는 이 상황을 “같은 키를 재사용했지만 요청 내용이 바뀐 충돌”로 안내하고, 클라이언트가 논리적 작업 구분과 UUID 생성을 확인하도록 해야 합니다.

## 실무에서 기억할 규칙

- 하나의 논리적 작업이 네트워크 문제로 다시 전송될 때는 같은 UUID를 유지합니다.
- 완전히 새로운 논리적 작업에는 새 UUID를 생성합니다.
- 같은 UUID로 요청 본문을 바꾸지 않습니다. 바꾸면 `409`가 발생합니다.
- 서버가 재시도를 자동으로 해주는 기능이라고 이해하지 않습니다. 이 기능은 동일 요청을 식별하고 최초 응답을 재사용하는 장치입니다.
- 서버의 최초 응답 보관 기간은 24시간입니다. 이 기간이 지나면 동일 키에 대한 동작은 이 문서에서 확인된 보관 규칙만으로 판단할 수 없으므로, 별도 운영 정책을 확인해야 합니다.

한 문장으로 요약하면, **같은 작업의 재전송에는 같은 UUID와 같은 본문을 사용하고, 새 작업에는 새 UUID를 사용해야 합니다.**
